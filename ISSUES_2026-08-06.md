## 1. Signup must show all plans, not just trial vs ₹100 — ✅ Fixed 2026-08-06

> "There is no drop down in payment section while we are taking subscription."
> Clarified: *"when owner signup they get two option either free or 100 rupees plan but it should show
> all pricing here with 14 days free [as one of them]."*

**Was:** [setup_academy_page.dart](apps/mobile/lib/features/dashboards/setup_academy_page.dart) offered
exactly two buttons — "Start 14-day free trial" and "Subscribe — ₹100/month" (the hardcoded `starter`
plan). No other plan was reachable at signup.

**Now:** the screen lists **every active plan** (from `availablePlansProvider` → `subscription_plans`,
cheapest first) as selectable rows, with the **14-day free trial as the first option and the default**.
Each row shows the plan name, its monthly price, and its caps ("500 students · 20 coaches · 3 centers").
One Continue button that reads either "Start 14-day free trial" or "Subscribe — ₹499/month" depending on
the selection; picking a paid plan passes that plan's code into the Razorpay checkout.

**Consequence:** the signup price list is now driven by the `subscription_plans` table — adding a plan or
changing a price in the database changes this screen with no app release.

## 2. Network failure during payment — ✅ Fixed 2026-08-06

> "If there is no internet or any network issue arise then it should be redirect to the payment
> subscription page."

**Was:** any connectivity failure surfaced as a snackbar wherever the user happened to be, with no way
to tell whether money had moved and no retry.

**Now:** a connectivity failure that happens **before a charge is possible** shows a dialog — *"No
internet connection. You haven't been charged. Reconnect and try again."* — with **Try again** and
**Close**. Retrying re-runs the payment on the spot. This is wired into all four places a payment can
start: the Plans/subscription page, the signup screen, the parent's dues list, and the fee-overdue lock
screen.

**On "redirect to the subscription page":** every owner payment already starts *on* the Plans page (the
dashboard Upgrade card and the Settings tile both open it first), so the retry keeps them exactly where
they need to be. The one exception is **signup**, where a failed payment leaves the academy on its free
trial — there the dialog's second button reads "Continue on free trial" and drops them on the dashboard,
which now carries the Upgrade card (#3).

**Deliberately not retried:** a failure while *confirming* a charge (`verify-…-payment`). The money may
already have moved, so those keep the existing "payment is being confirmed — we'll update shortly"
message and the webhook reconciles. Offering "try again" there would risk a second payment.

**Also fixed in passing:** if signup lost connection while *creating the academy*, the app used to
re-fetch the profile over the same dead connection and replace the screen with an error page. It now
keeps the owner on the setup screen with a plain retry message.

## 5. Student email not showing — ✅ Fixed 2026-08-08

> "Student dashboard his Email id Is not showing" … "Even in the owner dashboard."

**Root cause:** a student record has *two* email columns — the student's own (`email`, set when they're
invited with their own login) and the parent's (`parent_email`). The student's own address was captured
at creation and then had **no surface anywhere afterwards**: the edit form only ever showed "Parent
email", and the student/parent dashboard showed no email at all.

**Now:**
- **Owner side** — the student's profile shows a **Student email** field alongside Parent email, both
  editable and saved.
- **Student/parent side** — the dashboard header shows the email under the student's name: their own
  address when they have one, otherwise the parent's.

## 6. New student should not default to Active — ✅ Fixed 2026-08-08

> "When we create a Student by default it's showing active. This was pending from the old point — when
> owner has to mark active, or it should be active when he does payment."
> Answered by the owner: **both** — active on payment, and the owner can activate manually without one.

**New lifecycle:**
- A new student is created **Pending**, shown as an amber "pending" badge in the list. The status
  dropdown lists it first with the note *"Turns Active automatically on the first payment received."*
- **Any completed payment activates them** — an online payment or one an admin records by hand (cash,
  cheque, bank transfer) — because both write the same payments row and a database trigger does the flip.
- **The owner can still set Active by hand** at any time from the student's profile, no payment needed.
- Paused, Inactive and Graduated are deliberate decisions, so a payment never overrides them.

**Deliberate design note:** invoices are generated from batch enrolment, not from student status, so a
pending student still gets billed and can pay — which is what activates them. (If that ever changes, a
pending student would become unbillable and could never activate.)

**⚠️ Not live yet:** this needs the database migration
[20260808000000_student_pending_until_paid.sql](supabase/migrations/20260808000000_student_pending_until_paid.sql)
applied to the hosted project. Until it is, saving a student as "Pending" will be rejected by the
database.

## 7. Inventory — "0 20 piece", stock always zero — ✅ Fixed 2026-08-09

Screenshot (2026-08-09) shows the client's own items reading `0 20, piece` / `0 20 piece` /
`0 20 pieces`, while the demo-seeded items (`61 piece`, `30 piece`, `17 piece`) are fine.

**Root cause — a form trap, not a counting bug.** The **Unit** box was free text pre-filled "piece", so
the quantity was typed into it: the saved unit is literally `"20 piece"`. Stock stayed 0 because the
separate **Opening stock** field (pre-filled `0`, below the fold) was left alone. The list then prints
qty + unit — `0` + `20 piece` — which reads as "a 0 in front of my count".

**Fixed by making the mistake impossible:**
- **Quantity is now the first field** in Stock & cost — "Opening stock · How many you have right now,
  e.g. 30" — and no longer pre-filled with a `0` that looks already-answered.
- **Unit is now a picker** (piece, pair, set, box, packet, dozen, kg, gram, litre, metre) labelled
  "Unit (how it is counted)". "Other…" allows a custom measure but **rejects digits**, with the message
  *"No numbers here — put the quantity in Opening stock."*
- **The three broken items are repairable in place:** an item sitting at zero now shows a **Stock in
  hand** field when edited, so the count can be set without hunting for the movement sheet. (Items that
  already hold stock still change it through Purchase / Sale, so the stock history stays honest.)

Opening the affected items will now flag the unit `"20 piece"` as invalid — correcting it and entering
the quantity fixes each one.

## 8. Batch- and sport-wise price option — ✅ Fixed 2026-08-08 (carry-over, 13 June)

**What already worked:** billing per batch was possible — you create a price and assign it to a batch,
and every enrolled student gets billed. What was missing was the ability to say *"this price belongs to
this batch"*, so with several batches on different prices the fee list was an undifferentiated pile.

**Now:**
- The fee form has a **Batch (optional)** picker beside Sport. Picking a sport narrows the batch list to
  that sport's batches; picking a batch fills in its sport automatically.
- **"New fee" from inside a batch pre-tags that batch**, so creating a per-batch price is one step.
- The fee list shows the batch name on a batch-tagged price, so two "Monthly fee" entries at different
  prices are tellable apart.
- When assigning a fee to a batch, the picker now offers **only that batch's own prices plus the
  untagged academy-wide ones**, with the batch's own listed first. Another batch's price can no longer be
  picked by mistake.

**Unchanged on purpose:** who actually gets billed is still the assignment (batch assignment or a
per-student one). The tag scopes and labels the price; it does not silently bill anyone.
